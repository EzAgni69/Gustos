Gusto ERP: System Architecture & Monorepo Strategy1. The Architectural Strategy (First Principles)When building a system that spans Windows desktops (POS), Android tablets (KDS), mobile phones (Captain App), and cloud browsers (Admin ERP), the core problem is logic duplication. If the government changes GST from 18% to 12%, you should only update that logic in one place, not five.Recommendation: Stick with a Monorepo. A Monorepo (using Turborepo + pnpm workspaces) is definitively the most optimal approach for Gusto. The alternative—Polyrepos (separate repositories for each app)—will drastically slow down your development speed, cause version mismatch bugs (e.g., Captain App expects v2 of an API, but POS is running v1), and complicate cross-platform UI consistency.2. 3. Breakdown of Key Architectural DecisionsA. The packages/ Directory (The Secret Sauce)The success of this system relies entirely on strict boundaries.core-logic: This contains raw math. Functions like calculateCartTotal(items, taxes, discounts). By keeping it pure TypeScript without UI dependencies, both the Node.js api-gateway and the offline pos-desktop can import and run the exact same code.api-contracts: Using Zod, you define the exact shape of an order. If a developer tries to send an order from the app-captain without a table_number, TypeScript will throw a compilation error before the app even runs.print-engine: Abstracting thermal printer commands means if you change printer brands later, you only update this one package, and the POS automatically inherits the fix.B. Scalability: Separating api-gateway and sync-workerIn the cloud, you must handle two very different types of traffic:User Traffic (api-gateway): Managers looking at sales reports, updating menus, or checking inventory. This needs instant response times.Machine Traffic (sync-worker): 500 restaurant branches coming back online after an internet outage and dumping 10,000 offline orders at once, plus Zomato sending thousands of webhooks on a Saturday night.Solution: By splitting these into two Node.js apps, a massive dump of offline data (processed by sync-worker using Redis/RabbitMQ) will never slow down the manager trying to view their dashboard on the api-gateway.4. Addressing Edge Cases via the ArchitectureEdge Case 1: The "Polyfill" Problem (Web vs. Native vs. Desktop)The Risk: You accidentally import a Node.js filesystem (fs) module into a React Native app, crashing the mobile app instantly.The Monorepo Fix: Strict package scoping. ui-web is marked as React-only. ui-native is React Native-only. Turborepo will block cross-contamination during the build process.Edge Case 2: Multi-Franchise Overlap (Security)The Risk: A bug allows Franchise A to see Franchise B's customers.The Architecture Fix: The db-schema package implements PostgreSQL Row-Level Security (RLS) directly at the database schema level. Even if a junior developer writes a bad API query like SELECT * FROM orders, the database itself will intercept it and only return orders matching the logged-in user's franchise_id.Edge Case 3: Offline Data Conflict (The 2-Day Edit Window)The Risk: A bill is generated offline. It is edited locally on day 2. The internet comes back on day 3. How does the cloud know which version is true?The Architecture Fix: The offline-sync package dictates that the POS does not send state (e.g., "The bill is $50"); it sends events (e.g., "Event 1: Bill created $40", "Event 2: Item added $10"). The sync-worker in the cloud processes these events in chronological order based on the local timestamp, ensuring the cloud database mathematically rebuilds the exact truth, no matter when the internet restores.5. Alternatives to Monorepo (And why to avoid them)Alternative 1: Micro-Frontends / Microservices (Polyrepo)How it works: You create 10 different GitHub repositories. One for the POS, one for the Inventory service, one for the Auth service.Why you shouldn't use it: It requires a dedicated DevOps team just to keep the versions in sync. Overkill for a startup.Alternative 2: SubmodulesHow it works: Git submodules allow you to nest repositories inside each other.Why you shouldn't use it: Submodules are notorious for causing "detached head" states and merge conflicts. Monorepo tools like Turborepo have completely solved the problems submodules were trying to fix.
